## Q1：节点和状态是什么关系？为什么把状态写成类？

**问题**：节点和状态之间是怎样的关系？类为什么和状态契合、要把状态做成类？类像名词、方法像动词？

**回答**：
- 节点 = 动词（动作/逻辑），状态 = 名词（数据/东西）。
- 关系：节点是操作者，状态是被操作对象。节点读 `state.xxx` → 计算 → `return dict` 写回。
- 类 = 名词 + 动词统一体：属性（字段）描述"是什么"，方法描述"能干什么"。
- 状态天然是"一个东西带一堆属性"，类恰好是描述"东西 + 属性"的最优工具（需求匹配，非巧合）。
- 状态类被刻意做成"纯名词"（贫血模型：只有字段、没有自定义方法），动作交给节点函数。

## Q2：什么是枚举值？InquiryPhase 依据什么编写、取值哪里？

**问题**：什么是枚举值？InquiryPhase 枚举值依据什么编写、取值哪些地方？

**回答**：
- 枚举 = 把"有限的固定选项"打包成"有名字的常量"，只能选、不能乱写，写错立刻报错。
- `class InquiryPhase(str, Enum)` 是混合枚举：既有枚举约束，成员本身又是字符串（值如 `"CLARIFY"`）。
- 依据：问诊业务的流程图，每个阶段一个值（CLARIFY / GRAPH_QUERY / SYMPTOM_CONFIRM / COMPLICATION_CHECK / CONCLUDE / HANDOFF / END）。
- 取值 3 处：① state.py 初始默认值；② 节点 `return {"phase": ...}` 写；③ 路由函数 `if state.phase == ...` 读。
- 细节：`END = "__end__"` 对齐 LangGraph 内置结束标记；`COMPLICATION_CHECK` 定义了但当前未使用。

## Q3：为什么要写 InquiryState 主状态对象（黑板）？

**问题**：为什么要写 InquiryState？把 4 个类组合起来的"黑板"怎么通俗理解？

**回答**：
- 原因：节点是独立函数，局部变量用完即销毁，彼此无法共享数据。
- LangGraph 机制：节点接收 state，`return dict` 自动合并回 state，再传给下一节点。
- 通俗：InquiryState = 问诊现场的一块公共黑板；9 个节点 = 围着黑板干活的人，动作是"看黑板 → 做动作 → 写黑板"。
- 4 个类（InquiryPhase / CandidateDisease / PatientContext / InquiryHandoffPayload）都是需跨节点传递的数据，塞进黑板统一传递。
- 不用全局变量（多用户会互相污染）也不用数据库（每一步都读写太慢）。

## Q5：置信度在移交包里吗？为什么叫 primary_confidence？

**问题**：置信度似乎没在 InquiryHandoffPayload 里看到（以为字段名是 confidence_score）？

**回答**：
- 置信度在移交包里，字段名是 `primary_confidence`（不是 `confidence_score`），含义是"主诊断的置信度"。
- 记忆中的字段名与实际代码有差异：`recommended_exams`→`recommended_checks`、`inquiry_rounds`→`total_rounds`，且少了 `patient_id`/`patient_context`/`unmatched_symptoms`。
- 为什么加 primary 前缀：移交包只保留"主诊断（top1）"一个疾病的置信度；每个候选疾病各自的置信度在 `CandidateDisease.confidence`。
- 数据链路：`CandidateDisease.confidence` → 排序取 top1 → `top1.confidence` → 写入 `handoff.primary_confidence`（见 graph.py node_conclude 节点）。

## Q6：为什么 Agent 项目选择 Neo4j 图数据库？

**问题**：学过 Neo4j 图数据库，但不明确为什么这个 Agent 项目要用 Neo4j？它哪些特点符合需求？

**回答**（架构选型）：
- 图模型：7 类节点（Disease/Symptom/Drug/Department/Check/Food/Producer）+ 8 类关系（HAS_SYMPTOM/BELONGS_TO/COMMON_DRUG/RECOMMEND_DRUG/NEED_CHECK/DO_EAT/NO_EAT/ACOMPANY_WITH），由 `scripts/init_neo4j.py` 从 medical.json 构建。
- 项目里 3 个用途：① 症状标准化第二层（精确匹配标准症状名）；② `query_candidate_diseases` 候选疾病反查（症状反向沿 HAS_SYMPTOM 找疾病 + 命中率算基础置信度）；③ `enrich_candidate_details` 补齐科室/检查/并发症。
- 选型核心原因：① 医学知识本质是"实体+关系"的网，不是表；② 问诊是"症状→疾病→科室/检查/并发症"的多跳反向遍历，Cypher 天生擅长；③ 邻接存储找邻居 O(1)，实时快；④ 灵活加关系类型（医学知识持续扩展）；⑤ 精确关系推理，补向量检索只懂"相似"不懂"关系"的短板（GraphRAG：Neo4j 管确定关系 + Milvus 管语义兜底）。

## Q7：symptom_normalizer.py 实现的功能与流程（症状三层标准化）

**问题**：学习 `src/agents/inquiry/symptom_normalizer.py`，总结含义、功能、流程。

**回答**：
- 作用：症状三层标准化——把用户口语逐层兜底收敛成图谱真实存在的标准症状词，并提供反向"标准词→口语"用于追问。
- 9 个成员：`SymptomsOutput`(Schema)、`SYMPTOM_EXTRACT_PROMPT`、`extract_and_normalize_symptoms`(第一层 LLM 提取)、`match_symptoms_in_neo4j`(第二层 Neo4j 精确)、`SIMILARITY_THRESHOLD=0.85`、`semantic_match_symptoms`(第三层 Milvus 语义)、`normalize_symptoms`(总入口)、`SYMPTOM_HUMANIZE_PROMPT`、`humanize_symptoms`(反向口语化)。
- 正向流程：`extract_and_normalize_symptoms`(LLM 结构化输出，失败降级返回 []) → `match_symptoms_in_neo4j`(Cypher `IN $names` 精确匹配) → `semantic_match_symptoms`(Milvus `aembed_documents` 批量向量化 + `search` 取 distance≥0.85) → `normalize_symptoms` 汇总四件套 matched/mapped/unmatched/all_standard。
- 反向流程：`humanize_symptoms` 把标准词转口语（追问用），输出数组长度必须等于输入，否则退回原词保底。
- 关键点：① 第一层用 `with_structured_output`（唯一用它的地方）；② 第三层用 `aembed_documents`（复数批量）而非 `embed_query`；③ 四件套里 `all_standard = matched + mapped.values()`，供 Neo4j 查询用。
